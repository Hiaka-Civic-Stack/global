The Civic Stack Specs turn the Civic Stack Model into specification and
implementation guidance.

They are the contract layer for teams building, integrating or evaluating
Hiaka-compatible components.

Civic Stack Specs include the specs for every component of the Civic Stack
Model, including the Civic Design System.

For the Civic Design System, the specs cover its intent-driven and semantic
model as well as operational standards, conformance and reference
implementation artifacts.

## Responsibilities

The specs own:

* module specifications;
* design system specifications;
* blueprint specifications;
* shared service and interface specifications;
* API contracts;
* domain events;
* authorization rules;
* interoperability expectations;
* conformance guidance.

The specs should stay precise enough for implementation. They should not
become marketing copy or high-level conceptual storytelling.

## Specification Framework

Hiaka uses a Contract Kernel + Profiles model:

* the [Specification Framework](/framework) explains the system;
* [Normative Language](/framework/normative-language) defines `MUST`, `SHOULD`
  and `MAY` requirements;
* the [Common Spec Structure](/framework/common-spec-structure) defines the
  sections shared by every spec;
* Module, Blueprint, Civic Design System and Shared Service profiles extend the
  common structure for their component type.

Every specification declares one primary profile.

## Cross-Cutting Contracts

The contract layer currently defines:

* [API Conventions](/contracts/api-conventions);
* [Domain Events](/contracts/domain-events);
* [Authorization](/contracts/authorization);
* [Auditability](/contracts/auditability);
* [Interoperability](/contracts/interoperability);
* [Conformance](/contracts/conformance).

Each normative requirement has a stable domain-scoped identifier. Conformance
is evidence-based: a product or component must point to inspectable contracts,
tests, policies, schemas or reviews for every applicable mandatory requirement.

## Repository Boundary

Mintlify presents the current specs as one navigable portal. As Hiaka matures,
canonical contracts may move to dedicated component or contract repositories
with their own release cycles. The portal should continue to provide a coherent
entry point without pretending that all implementations live in this hub.
