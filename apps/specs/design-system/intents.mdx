---
title: "Intent Layer"
description: "Civic jobs that Hiaka-compatible products should design around."
---

The Intent Layer names the civic jobs people need to complete in a public
participation product.

It is the first layer of the Civic Design System Conceptual Model.

```text
Civic Design System
  -> Conceptual Model
       -> Intent Layer
       -> Semantic Layer
       -> Pattern Layer
```

Intent-driven design prevents teams from starting with screens, generic
workflows or component inventory. A product surface should first be justified
by the civic job it helps people complete.

## Core Intents

Initial civic intents:

* [understand a public process](/design-system/intents/understand-process);
* [know whether one can participate](/design-system/intents/know-participation-eligibility);
* [contribute to a bounded civic process](/design-system/intents/contribute-bounded-process);
* compare, discuss or deliberate around public input;
* verify an official response, decision or rationale;
* follow a decision, commitment or implementation progress.

## Spec Structure

Intent specs follow the [Design System Spec Structure](/design-system/spec-structure).

An intent spec should define the civic job, required semantic concepts,
patterns that can realize it, module touchpoints and conformance checks.

## Sprint 1A Specs

The first detailed intent specs are:

## Review Questions

Use these questions when designing or reviewing a product surface:

* Which civic job is the person trying to complete?
* Which actor owns the next step?
* Which status, deadline, eligibility rule or territorial scope affects the
  job?
* Which evidence or public record should be visible?
* Which Civic Design System pattern realizes the intent?

## Non-Goals

The Intent Layer does not define module business rules, API contracts or visual
components.

Those decisions belong respectively to Civic Modules, Civic Stack Specs and
reference implementation artifacts.
