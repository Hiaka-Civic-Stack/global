<Note>**Status: draft.** This profile is normative but not yet stable.</Note>

The Module Profile extends the [Common Spec Structure](/framework/common-spec-structure)
for a reusable Civic Module.

A Module specification describes one coherent civic capability. It must remain
usable across multiple Civic Blueprints.

## Required Sections

In addition to the common core, a Module specification must define:

* domain concepts and invariants;
* functional requirements and their capability classification;
* non-functional requirements and measurable evidence;
* commands and queries;
* Domain Events;
* API surface;
* authorization policies;
* persistence boundaries;
* external ports;
* test expectations.

The [Module Specification Baseline](/modules/specification-baseline) defines
the required document suite, requirement metadata and `Core + Optional
Capabilities` conformance model.

## Domain Boundary

The specification must state which business rules and state transitions the
Module owns. It must also identify adjacent capabilities that belong to another
Module, a Civic Blueprint, the Civic Design System or a Shared Digital Service.

Under `SPEC-006`, a Module remains independent from any single Civic Blueprint.
Blueprint names can appear in examples, but they do not become required runtime
dependencies.

## Contracts

The Module specification must identify applicable requirements from:

* API conventions;
* Domain Events;
* authorization;
* auditability;
* interoperability;
* conformance.

Under `API-003`, transport DTOs are not presented as domain entities.
Persistence records remain separate for the same boundary reason.
Infrastructure implementations stay behind ports declared by the application
or domain boundary.

## Expected Evidence

Evidence should include:

* domain and application tests;
* API contract tests;
* event schemas and producer tests;
* authorization policy tests;
* persistence integration tests;
* adapter contract tests.

Every normative Module requirement must appear in a conformance matrix linking
the requirement to observable behavior, an interface where applicable, the
expected evidence and an evaluation result.

## Non-Goals

This profile does not define one Module's business model. It does not require a
microservice deployment, one database technology or one application framework.
